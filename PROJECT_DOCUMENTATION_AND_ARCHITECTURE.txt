1. EXECUTIVE SUMMARY & CORE PLATFORM PURPOSE
====================================================================================================
MachineGuard is an industrial-grade, AI-powered predictive maintenance and real-time SCADA monitoring 
platform designed for high-value factory equipment (CNC Milling Centers, High-Pressure Centrifugal 
Pumps, Hydraulic Stamping Presses, Rotary Screw Air Compressors, and 6-Axis Welding Robots).

The core mission of the platform is to eliminate unplanned downtime, prevent catastrophic mechanical 
failures, and extend machinery lifespan by combining:
1. Real-time physical sensor telemetry ingestion (air & process temperatures, spindle speeds, drive 
   torques, tool wear, vibrations, and pneumatic/hydraulic pressures).
2. Dual Machine Learning Condition Assessment:
   - Failure Risk Classification: Random Forest estimating probability of failure [0.0% - 100.0%].
   - Operational Anomaly Detection: Isolation Forest estimating multi-parameter cluster divergence.
   - Remaining Useful Life (RUL): Gradient Boosted Regressor predicting remaining production cycles.
3. Multi-Model Consensus & Disagreement Detection: Identifies subtle deviations where one model detects 
   outlier behavior before failure thresholds are breached.
4. Autonomous Incident Operations: Automatically creates, tracks, acknowledges, and verifies incidents.
5. Automated Recovery Verification: Confirms 3 consecutive healthy cycles before resolving an incident.
6. Low-Latency Hybrid Cloud Architecture: Real-time browser telemetry synchronization via Supabase 
   Mumbai (ap-south-1) with < 20 ms round-trip latency.

      * --fault pressure : Pneumatic/hydraulic seal cavitation (< 1.8 bar) or line blockage (> 8.5 bar).

4. MACHINE LEARNING MODELS SPECIFICATION & DIAGNOSIS MECHANICS
====================================================================================================

MachineGuard utilizes three distinct, mathematically rigorous machine learning models trained on 
empirical industrial telemetry:

----------------------------------------------------------------------------------------------------
MODEL 1: AI4I Random Forest Failure Classifier (Failure Probability)
----------------------------------------------------------------------------------------------------
- Algorithm           : Scikit-Learn RandomForestClassifier (100 estimators, balanced class weights).
- Training Dataset    : UCI AI4I 2020 Predictive Maintenance Dataset (10,000 industrial records).
- Input Features (5)  : Air Temperature [K], Process Temperature [K], Rotational Speed [rpm], 
                        Torque [Nm], Tool Wear [min].
- Output Metrics      : Raw Decimal Probability [0.0 - 1.0], Binary Flag (0: Normal, 1: Failure).
- Classification Rule :
  * Probability >= 0.60 (60.0%) -> High / Critical Risk (Failure predicted).
  * Probability 0.30 - 0.59      -> Moderate Risk (Elevated wear / parameter drift).
  * Probability < 0.30           -> Nominal Operation (Healthy).
- Physical Failure Modes Modeled:
  * Heat Dissipation Failure (HDF)
  * Power Failure (PWF)
  * Overstrain Failure (OSF)
  * Tool Wear Failure (TWF)

----------------------------------------------------------------------------------------------------
MODEL 2: AI4I Isolation Forest Outlier Estimator (Operational Anomaly Detection)
----------------------------------------------------------------------------------------------------
- Algorithm           : Scikit-Learn IsolationForest (contamination=0.035, 150 isolation trees).
- Principle           : Recursive random sub-sampling isolating atypical multi-parameter sensor 
                        correlations in sparse multidimensional space.
- Decision Boundary   : 0.0000 Decision Score.
  * Decision Score < 0.0000 -> Anomaly (Statistical outlier / unusual mechanical dynamics).
  * Decision Score >= 0.0000 -> Normal (Within standard operating cluster).
- Crucial Distinction : Anomaly detection flags unusual operating behavior (e.g., elevated vibration 
  or atypical torque spikes) even when the machine has not yet reached failure threshold.

----------------------------------------------------------------------------------------------------
MODEL 3: PHM 2010 High-Speed Milling Regressor (Remaining Useful Life / RUL)
----------------------------------------------------------------------------------------------------
- Algorithm           : GradientBoostingRegressor / Linear Pipeline.
- Training Dataset    : PHM 2010 High-Speed CNC Milling Cutter Flank Wear Dataset.
- Target Output       : Estimated production cycles remaining before cutting tool reaches the critical 
                        240.0-minute flank wear replacement boundary.
- Prescriptive Action : When remaining cuts drop below 50, system alerts operators to schedule tool 
  insert replacement before the next production shift.

----------------------------------------------------------------------------------------------------
MODEL CONSENSUS & DISAGREEMENT ENGINE
----------------------------------------------------------------------------------------------------
MachineGuard actively compares Model 1 and Model 2:
- If Random Forest indicates Normal (< 30% risk) but Isolation Forest flags an Anomaly (Score < 0):
  * Sets model_disagreement = True.
  * Displays a prominent "Model Consensus Notice" on the machine SCADA view.
  * Explains that sensor dynamics are statistically abnormal and flags the unit for advisory inspection 
    before catastrophic failure can develop.

5. DATABASE SCHEMA, TABLES & SECURITY INFRASTRUCTURE
====================================================================================================

The database runs on Supabase PostgreSQL 17 in the South Asia (Mumbai, ap-south-1) region.

----------------------------------------------------------------------------------------------------
DATABASE TABLES:
----------------------------------------------------------------------------------------------------
1. machines
   - Columns: id, machine_id (PRIMARY KEY), name, machine_type, location, description, type_variant, 
     status, created_at, updated_at.
   - Purpose: Master asset catalog.

2. sensor_readings
   - Columns: id, machine_id (FK -> machines ON DELETE CASCADE), timestamp, air_temperature, 
     process_temperature, rotational_speed, torque, tool_wear, vibration, pressure, power_consumption, 
     operating_load.
   - Purpose: High-speed time-series physical telemetry packets.

3. predictions
   - Columns: id, telemetry_id (FK -> sensor_readings ON DELETE CASCADE), machine_id (FK -> machines 
     ON DELETE CASCADE), timestamp, failure_probability, risk_category, failure_prediction, 
     anomaly, anomaly_score, anomaly_label, estimated_remaining_cuts, rul_unit, machine_health_status, 
     model_disagreement, disagreement_reason, contributing_factors, recommendation.
   - Purpose: Synchronized ML diagnosis records.

4. alerts
   - Columns: id, machine_id (FK -> machines ON DELETE CASCADE), timestamp, title, severity, 
     category, status (ACTIVE, RESOLVED), message, triggering_values, acknowledged_at, resolved_at.
   - Purpose: Operational alarms and notifications.

5. incidents
   - Columns: id, incident_id (PRIMARY KEY), machine_id (FK -> machines ON DELETE CASCADE), 
     machine_name, fault_type, severity, status (Open, Acknowledged, Under Maintenance, 
     Verification Pending, Resolved), root_cause, resolution_notes, created_at, resolved_at.
   - Purpose: Maintenance work tickets and incident management.

6. maintenance_logs
   - Columns: id, machine_id (FK -> machines ON DELETE CASCADE), technician_name, action_taken, 
     parts_replaced, downtime_minutes, performed_at.
   - Purpose: Physical repair audit trails.

7. incident_verifications
   - Columns: id, incident_id (FK -> incidents ON DELETE CASCADE), machine_id (FK -> machines 
     ON DELETE CASCADE), verified_at, status, consecutive_healthy_cycles, required_healthy_cycles, 
     verification_details.
   - Purpose: Automated 3-cycle post-repair verification records.

----------------------------------------------------------------------------------------------------
ROW LEVEL SECURITY (RLS) & REALTIME CONFIGURATION:
----------------------------------------------------------------------------------------------------
- Every table has RLS enabled (ALTER TABLE ... ENABLE ROW LEVEL SECURITY).
- Permissions for anon and authenticated:
  * machines: SELECT, INSERT, UPDATE, DELETE
  * sensor_readings: SELECT, INSERT, DELETE
  * predictions: SELECT, INSERT, DELETE
  * alerts: SELECT, INSERT, UPDATE, DELETE
  * incidents: SELECT, INSERT, UPDATE, DELETE
  * maintenance_logs: SELECT, INSERT, UPDATE, DELETE
  * incident_verifications: SELECT, INSERT, UPDATE, DELETE

6. COMPLETE HISTORY OF DEVELOPMENT, KEY BUGS DIAGNOSED & RESOLUTIONS
====================================================================================================

Throughout development and hardening, several critical engineering challenges were systematically 
identified, debugged, and resolved:

1. AUSTRALIA TO MUMBAI SUPABASE MIGRATION (100x Latency Reduction)
   - Problem: Initial database was hosted in Australia (ap-southeast-2). Round-trip queries took 
     40-45 seconds, causing timeouts on Vercel and slow dashboard rendering.
   - Resolution: Migrated the entire schema to a new Supabase project in Mumbai (ap-south-1). Latency 
     dropped to 18 milliseconds, enabling instant 5.0s telemetry streaming.

2. VERCEL SPA ROUTING & API PROXYING
   - Problem: In vercel.json, the catch-all rewrite /(.*) -> /index.html caused calls to /api/health to 
     return index.html (HTTP 200 with HTML text), causing JSON parse errors in the browser.
   - Resolution: Configured frontend/src/api.js to query Supabase directly from the browser for all data 
     fetching, and only attempt http://localhost:8000/api when the local edge backend is active.

3. "OPEN MONITORING" BLANK WHITE SCREEN CRASH
   - Problem: Clicking "Open Monitoring" for any machine on Vercel produced a blank white screen.
   - Root Causes Found:
     * Cause A: MachineDetail.jsx invoked useRef(false) without importing useRef from 'react' 
       (ReferenceError: useRef is not defined).
     * Cause B: JavaScript type coercion error on temperature: The code checked 
       latestReading.temperature !== null. In Supabase, temperature is undefined, and undefined !== null 
       evaluates to true in JS. Calling .toFixed(1) on undefined threw an unhandled TypeError.
     * Cause C: fetchMachineDetail only queried the bare machines table, returning records without 
       latest_reading or latest_prediction.
   - Resolution:
     * Added useRef and Component to React imports.
     * Wrapped the monitoring view in a dedicated React MachineErrorBoundary.
     * Replaced raw null-checks with strict typeof val === 'number' guards across all sensor tiles.
     * Upgraded fetchMachineDetail to concurrently fetch latest reading, prediction, and alert counts.

4. POLYMORPHIC contributing_factors.join TYPE ERROR
   - Problem: The error boundary reported: y.contributing_factors.join is not a function.
   - Root Cause: In PostgreSQL, contributing_factors was stored as a string or JSON string. Strings in 
     JavaScript do not have a .join() method.
   - Resolution: Built formatContributingFactors(factors) helper that safely handles Arrays, JSON 
     strings, plain strings, and objects without ever crashing.

5. PERSISTENT FALSE "3" ALERT BADGE & RED DASHBOARD BOX
   - Problem: The sidebar showed a red badge with "3" and the dashboard showed a red critical box even 
     when all incidents on screen were marked RESOLVED.
   - Root Cause: In Supabase, resolved incidents were stored with status 'Resolved'. The frontend checked 
     i.status !== 'RESOLVED' (case-sensitive), which evaluated to true!
   - Resolution: Converted to case-insensitive check (String(status).toUpperCase() !== 'RESOLVED'). 
     When unresolved count is 0, the red badge is completely hidden, and the dashboard displays the clean 
     green Nominal Fleet Condition banner.

6. GLITCH-FREE MACHINE DELETION
   - Problem: Deleting a machine caused UI flickering or database errors.
   - Root Cause: PostgreSQL RLS policies lacked DELETE permissions for the anon role on child tables, 
     blocking CASCADE deletion.
   - Resolution: Added DELETE policies on all tables in Supabase Mumbai, updated deleteMachine to cleanly 
     delete child records first, and added optimistic state updates in App.jsx.

7. TELEMETRY CYCLE TUNING & INDUSTRIAL UI AESTHETIC
   - Problem: 1.0s telemetry was generating excessive WAN traffic, and "Paused on Laptop" labels looked 
     like an unfinished prototype.
   - Resolution: Tuned telemetry cycle to 5.0 seconds across data_generator.py and frontend timers. 
     Replaced all prototype labels with professional industrial statuses (Cloud Standby, Model Ready, 
     5.0s Cycle).
